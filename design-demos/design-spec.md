# 企业知识库 RAG UI 全面升级 · 三方向共同设计规格

## 项目理解

这是一个面向企业私有文档的知识库问答系统，现有前端已经覆盖知识库 CRUD、成员权限、文档上传与解析、流式问答、引用溯源、任务中心、质量评测、系统监控和管理员后台。当前主要问题不是功能缺失，而是信息架构把普通用户任务与研发、运维、调试能力放在了同一层：向量同步、检索调试、模型名称、综合分/向量分/关键词分、缓存命中、运行配置、数据库与 Redis 状态、API 地址、任务原始日志等概念被直接暴露，导致页面看起来像工程演示台，不像企业员工愿意长期使用的知识产品。同时左侧知识库信息编辑与成员管理长期占据主工作区，问答和阅读空间被压缩。

目标不是简单“换皮”，而是重新定义产品的前台与后台边界：普通员工进入系统后，应当快速选择知识范围、提出问题、阅读可信答案、核对引用来源和继续追问；内容管理员应当能管理文档、成员和可理解的处理状态；系统管理员才可进入高级诊断查看模型、向量、缓存、组件健康和日志。后台能力不能被删除，但必须通过角色权限、二级入口、抽屉/弹层和渐进披露管理，默认不进入普通用户视线。

## 目标受众与核心场景

- 普通员工：搜索公司制度、项目资料、技术文档；最关心答案是否可信、来源在哪里、资料是否在权限范围内。
- 知识库管理员：上传与整理资料、查看哪些文件可用于问答、处理失败文件、管理协作者。
- 系统管理员：排查模型、索引、队列、缓存、基础设施和质量问题；这类内容只在管理员专属区域出现。
- 桌面端为主，观众距离约 1 米，目标视口统一为 1440×900；同时确保 1024px 宽度仍可用。

## 共同页面内容

三版都围绕同一“问答工作区”主场景完成，并至少包含：知识空间选择、会话历史、核心提问输入、一个已有答案、两条可读的引用来源、文档入口、用户菜单、可发现但不抢眼的管理入口。示例问题统一使用「Java-Redis 项目中的文档解析失败后，系统会如何处理？」；示例答案只能根据仓库 README 与现有界面能力做概括，不得编造业务数据。引用只展示文档名、章节/页码式定位和内容摘要；普通视图不展示 chunk ID、模型名、向量分数、关键词分数、缓存命中、耗时等内部实现信息。

## 信息分层与隐私边界

### 普通用户默认可见

- 知识库/知识范围名称、自己的访问角色（必要时）、最近会话、问题与答案。
- 引用文档名、可读定位、更新时间、简短摘录。
- 文档“可用 / 处理中 / 需处理”这类业务语言，不出现解析器、Embedding 或向量同步术语。
- 一个低干扰的“管理”入口；无权限用户不显示。

### 内容管理员按需可见

- 文档上传、成员管理、失败文件重试、知识库设置、导入导出。
- 任务状态翻译成可行动的描述，例如「正在建立可检索内容」「需要重新处理」。

### 系统管理员二级入口可见

- 模型名称与端点、Embedding 配置、向量库、Redis、缓存 TTL、限流、运行健康、诊断建议、原始日志、检索分数组成。
- 这些信息放在“高级诊断”抽屉或独立管理区，打开前明确提示仅供管理员排障；原型中可展示一小段被遮罩/概括的诊断条目，以证明层级存在，但不能默认铺在主页面。

## 视觉与交互要求

- 三版必须在视觉、布局和交互哲学上明显不同，但都要像真实产品，而不是风格海报。
- 纯 HTML/CSS/少量原生 JavaScript，自包含单文件，双击可打开；不依赖网络字体和图片。
- 使用 Lucide 风格的简洁线性图标可用内联几何符号或文字替代，但不画人物、设备等 SVG imagery，不使用 emoji。
- 禁止紫粉蓝通用渐变、装饰性指标卡、虚构统计、每个标题配图标、圆角卡片加左彩色边框、统一深蓝霓虹 SaaS 套路。
- 中文正文不小于 14px，可点击区域尽量达到 44px；键盘焦点清晰；颜色对比满足正文可读性。
- 至少实现三个真实交互：切换知识空间或会话、点击引用展开来源、点击管理/高级诊断并体现权限分层。可额外实现新建对话、来源筛选或侧栏收起。
- HTML 顶部必须保留 assumptions/reasoning 注释，明确这是方向探索而非生产实现。

## 三版独立锚点

1. 秒数轮盘：本轮秒数为 19，`19 % 20 + 1 = 20`，使用网页风格库第 20 号「日式留白白盒画廊」作为排版锚点；将“内容图”替换为答案与来源内容本身，强调安静、克制、UI 退隐。
2. 现实参照：以 Glean/Notion Enterprise Search 的“先问问题、答案带引用、公司知识范围可控”产品逻辑为迁移参照，不复制品牌资产；视觉必须结合本项目，而不是仿站。
3. 最佳设计团队：以 IBM Carbon 企业产品团队的渐进披露、强层级、可访问组件与复杂性按需出现为设计思路，做更适合管理员和长期企业使用的专业版本。

## 图片需求判断

这是工具、文档与数据型界面，内容核心是问答、来源与状态，图片不是内容必需。三版不取装饰图库，不用 stock photo，不留无意义的 hero 图片位；把精力集中在信息架构、中文排版、交互反馈和前后台边界。
