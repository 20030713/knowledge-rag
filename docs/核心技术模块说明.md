# 核心技术模块说明

这份文档用于记录系统中比较有技术含量、适合面试讲解的模块。后续新增异步任务、消息队列、分布式锁、向量检索、缓存一致性等模块时，都继续追加到这里。

---

## 1. 异步文档解析模块

### 背景

文档解析包含：

```text
读取文件 -> 提取文本 -> 清洗文本 -> 文本切分 -> 写入 document_chunk -> 更新文档状态
```

如果这个过程放在 HTTP 请求里同步执行，文件稍大时会导致请求长时间等待、接口超时、请求线程被占用，用户也无法感知后台进度。

### 使用技术

- Spring `@EnableAsync`
- Spring `@Async`
- `ThreadPoolTaskExecutor`
- MyBatis-Plus
- 文档状态机
- 前端轮询

### 系统中的运行方式

1. 用户点击“解析”。
2. 前端调用 `POST /api/doc/{id}/parse`。
3. 后端校验文档归属。
4. 后端把文档状态更新为 `PARSING`。
5. 后端提交异步解析任务并立即返回。
6. 前端轮询 `GET /api/doc/{id}/status`。
7. 后台线程读取文件、切分 chunk、写入 `document_chunk`。
8. 成功后更新为 `COMPLETED`，失败后更新为 `FAILED`。

### 为什么拆成独立组件

Spring 的 `@Async` 基于代理实现。如果在同一个类里直接调用自己的 `@Async` 方法，本质是普通 Java 方法调用，不会经过 Spring 代理，异步不会生效。

所以系统把后台任务拆到：

```text
src/main/java/com/rag/knowledge/job/DocumentParseTask.java
```

由 `DocumentServiceImpl` 调用 `DocumentParseTask.parseAsync()`，确保异步代理生效。

### 面试讲法

可以这样介绍：

```text
文档解析属于耗时任务，所以我没有把它放在 HTTP 请求里同步执行，而是使用 Spring @Async 和独立线程池异步处理。接口只负责校验文档、标记 PARSING 并提交任务，然后立即返回。前端通过轮询状态接口感知进度。为了避免 @Async 同类自调用失效，我把解析逻辑拆成独立的 DocumentParseTask 组件。
```

## 2. 异步任务失败重试保护

### 背景

文档解析可能因为文件为空、格式不支持、文件路径异常等原因失败。如果只把状态改为 `FAILED`，用户可能反复点击“重新解析”，导致后台重复执行无效任务。

### 使用技术

- 文档状态机
- MySQL 字段 `retry_count`
- Spring 异步任务
- 前端状态展示与按钮禁用

### 数据设计

`document` 表新增：

```text
retry_count INT NOT NULL DEFAULT 0
```

含义：当前文档连续解析失败次数。

### 系统中的规则

- 上传新文档时，`retry_count = 0`
- 解析成功后，`retry_count` 清零
- 解析失败后，`retry_count + 1`
- 文档正在 `PARSING` 时，不允许重复提交解析任务
- `retry_count >= 3` 时，拒绝继续解析，提示用户检查文件后重新上传

### 面试讲法

可以这样介绍：

```text
异步任务不能只做状态流转，还要考虑失败后的重试控制。我在 document 表中增加 retry_count 记录连续失败次数，成功后清零，失败后递增，超过 3 次就拒绝继续提交任务，避免用户反复触发无效后台任务。
```

## 3. 异步任务监控视图

### 背景

异步任务如果只在后台执行，用户很难判断系统是否真的在工作。因此系统在仪表盘中增加“解析任务”视图，展示最近失败或正在解析的文档。

### 当前展示内容

- 文档名
- 当前状态
- 更新时间
- 失败次数
- 失败原因

### 系统价值

这个视图让异步处理从“后台黑盒”变成“可观察任务”：

- 用户能看到哪些文档还在解析
- 用户能看到哪些文档失败了
- 用户能看到失败次数是否达到上限
- 后续可以自然扩展成完整任务中心

### 代码位置

```text
src/main/java/com/rag/knowledge/service/impl/DashboardServiceImpl.java
frontend/src/main.tsx
```

### 面试讲法

可以这样介绍：

```text
我在仪表盘里增加了解析任务监控，把最近失败或解析中的文档展示出来。这样异步任务不是只在后端跑，用户可以看到任务状态、失败次数和失败原因。当前是轻量版，直接基于 document 状态查询；后续任务类型变多后可以抽象成 task_record 表和任务中心。
```

## 4. 本地 Embedding 与向量检索模块

### 背景

关键词检索版 RAG 能跑通主流程，但它依赖字面匹配，面对同义表达、长问题或语义相近但用词不同的场景时，召回效果有限。

为了让系统具备真正 RAG 检索层的结构，当前新增了 Embedding 抽象和本地向量检索实现。这个版本不依赖外部模型，也不需要安装向量数据库，适合在本地稳定演示；后续可以替换成真实 Embedding 模型和 Milvus / pgvector。

### 使用技术

- Embedding 服务接口
- Hashing Vectorizer
- L2 归一化
- Cosine Similarity 余弦相似度
- 向量相似度 + 关键词分数混合排序
- Spring Bean 接口抽象

### 系统中的运行方式

当前实现位于：

```text
src/main/java/com/rag/knowledge/vector
```

核心接口：

```text
TextEmbeddingService
VectorSearchService
```

当前默认实现：

```text
HashingTextEmbeddingService
LocalVectorSearchService
```

问答流程变为：

```text
用户问题 -> 生成问题向量 -> 查询当前知识库 chunk -> 生成 chunk 向量 -> 计算余弦相似度 -> 融合关键词分数 -> 返回 Top K 引用片段 -> 生成回答
```

### Hashing Vectorizer 原理

Hashing Vectorizer 不需要训练模型。它会把文本切成 token，然后把每个 token 通过 hash 映射到固定维度的向量位置上。

例如当前使用 256 维向量：

```text
token -> hash(token) -> index in [0, 255] -> vector[index] += 1
```

之后对向量做 L2 归一化，让不同长度的文本可以比较相似度。

### 为什么要保留关键词分数

Hashing 向量很轻量，但不是大模型语义 Embedding。为了让中文问题和明确术语更稳定命中，系统采用混合排序：

```text
最终分数 = 向量相似度 * 0.7 + 归一化关键词分数 * 0.3
```

这样既有向量检索的结构，又保留关键词匹配对专业词、项目名、技术名的优势。

### 可调参数

向量检索参数统一放在：

```yaml
app:
  vector-search:
    top-k: 5
    max-chunks-to-scan: 200
    dimensions: 256
    vector-weight: 0.7
    keyword-weight: 0.3
```

含义：

- `top-k`：最终返回多少个引用片段
- `max-chunks-to-scan`：本地检索最多扫描多少个 chunk
- `dimensions`：Hashing 向量维度
- `vector-weight`：向量相似度权重
- `keyword-weight`：关键词命中权重

这些配置让系统具备基本调优能力。例如回答引用太少时可以增大 `top-k`；关键词命中太强时可以提高 `vector-weight`；本地文档变多时可以提高 `max-chunks-to-scan` 或升级为真实向量库。

### 检索透明度

为了方便调试和面试演示，引用片段会返回三类分数：

```text
score        -> 最终混合分数
vectorScore  -> 本地向量余弦相似度
keywordScore -> 关键词命中分数
```

前端在引用来源中展示这些分数，用户可以看到每个片段为什么排在前面。这也方便后续替换真实向量库时对比召回效果。

### 当前版本的边界

当前的 Hashing 向量不是语义大模型 Embedding，它不能真正理解“同义词”和复杂语义关系。它的价值主要是：

- 先把向量检索架构搭起来
- 本地不依赖外部 API
- 让 RAG 服务通过接口依赖检索层
- 后续替换真实向量库时改动范围小

### 后续升级方向

后续可以把实现替换为：

- LangChain4j + 本地或云端 Embedding 模型
- Milvus
- PostgreSQL pgvector
- Elasticsearch dense vector

替换时优先保持 `VectorSearchService` 接口不变，让 `RagServiceImpl` 不感知底层实现变化。

### 面试讲法

可以这样介绍：

```text
我没有把 RAG 检索逻辑直接写死在业务层，而是抽象了 TextEmbeddingService 和 VectorSearchService。当前为了本地可演示，使用 Hashing Vectorizer 生成 256 维向量，再用余弦相似度召回 chunk，并融合关键词分数排序。这个实现不是最终的语义 Embedding，但它让系统具备向量检索的完整结构，后续可以平滑替换成 Milvus、pgvector 或真实 Embedding 模型。
```

## 5. 多格式文档解析模块

### 背景

RAG 系统的第一步是把用户上传的文件变成可检索文本。如果上传入口支持 PDF 和 Word，但解析器只支持 TXT / Markdown，用户体验会割裂：文件能上传，却不能进入 RAG 流程。

因此系统扩展了文档文本提取能力，让上传支持范围和解析支持范围保持一致。

### 使用技术

- JDK `Files.readString`
- Apache PDFBox
- Apache POI `poi-ooxml`
- Apache POI `poi-scratchpad`
- 统一文档读取入口
- 异步解析任务

### 当前支持格式

```text
txt  -> UTF-8 文本读取
md   -> UTF-8 文本读取
pdf  -> PDFBox 提取页面文本
docx -> Apache POI XWPF 提取文本
doc  -> Apache POI HWPF 提取文本
```

### 系统中的运行方式

文档读取入口位于：

```text
src/main/java/com/rag/knowledge/storage/TextDocumentReader.java
```

异步解析任务调用读取器：

```text
DocumentParseTask -> TextDocumentReader.read() -> TextChunker.split() -> document_chunk
```

读取器根据文件后缀分发到不同解析方式：

```text
PDF  -> PDFBox
DOCX -> XWPFDocument + XWPFWordExtractor
DOC  -> HWPFDocument + WordExtractor
TXT/MD -> Files.readString
```

### 为什么不用字符串硬解析

PDF 和 Word 都不是纯文本文件，不能直接按字符串读取：

- PDF 有页面、字体、坐标和对象结构
- DOCX 本质是 Office Open XML 压缩包
- DOC 是旧版二进制 Word 格式

所以系统使用成熟库提取文本，避免自己解析复杂文件格式。

### 当前版本的边界

当前只提取正文文本，不处理：

- 图片 OCR
- 扫描版 PDF
- 表格结构还原
- 页眉页脚精细过滤
- 复杂排版语义

这符合当前 MVP 目标：先把常见文档内容稳定进入 chunk 和 RAG 流程。

### 后续升级方向

- 扫描版 PDF 接入 OCR
- 表格单独提取为结构化 chunk
- 为不同文件格式实现 `DocumentTextExtractor` 插件化接口
- 记录解析耗时、页数、段落数等元数据

### 面试讲法

可以这样介绍：

```text
我把文档解析统一封装成 TextDocumentReader，根据文件类型选择不同解析器。TXT 和 Markdown 使用 UTF-8 读取；PDF 使用 PDFBox；DOCX 和 DOC 使用 Apache POI。这样上传入口和解析能力保持一致，后续如果要支持 OCR 或表格结构化，只需要扩展文档读取层，不影响异步任务、切分和 RAG 检索流程。
```

## 6. 轻量任务中心

### 背景

系统已经有异步文档解析、失败重试和 Redis 分布式锁。如果用户只能在文档列表里看到单个文件状态，整体任务视角仍然不够清晰。

因此系统在仪表盘中扩展了任务中心，用于统一查看文档解析任务。

### 使用技术

- 文档状态机
- MyBatis-Plus 条件查询
- 前端状态筛选
- 异步任务重试入口
- Redis 分布式锁复用

### 当前能力

任务中心支持：

- 查看最近文档解析任务
- 按状态筛选：`ALL / UPLOADED / PARSING / COMPLETED / FAILED`
- 查看失败次数和失败原因
- 对未超过重试上限的失败文档重新提交解析

### 接口设计

```http
GET /api/dashboard/tasks?status=FAILED&limit=20
```

参数：

```text
status -> 可选，默认 ALL
limit  -> 可选，默认 20，最大 100
```

### 系统中的运行方式

1. 前端任务中心按状态请求任务列表。
2. 后端只查询当前登录用户的文档，保证用户隔离。
3. 用户点击失败任务的“重试”。
4. 前端调用已有文档解析接口。
5. 后端复用解析重试保护和 Redis 分布式锁。
6. 任务状态更新后，前端刷新任务中心。

### 为什么不立刻新建 task_record 表

当前系统只有一种后台任务：文档解析。直接复用 `document` 状态字段可以减少表结构复杂度，也能满足当前演示需求。

当后续出现更多任务类型时，例如：

- 文档 OCR
- Embedding 批量生成
- 向量库重建
- 知识库导入导出

再抽象独立的 `task_record` 表会更合适。

### 面试讲法

可以这样介绍：

```text
我在异步解析的基础上做了一个轻量任务中心。当前任务类型只有文档解析，所以先复用 document 表里的状态、失败次数和错误信息，提供按状态筛选和失败重试。重试仍然走原来的解析接口，因此会复用失败次数保护和 Redis 分布式锁。后续任务类型变多后，可以平滑抽象成 task_record 表。
```

## 7. 知识库删除级联清理

### 背景

知识库是文档、切片、问答历史和 RAG 缓存的上层边界。如果删除知识库时只删除 `knowledge_base` 主表，会留下大量孤儿数据。

### 当前清理范围

删除知识库时会同步清理：

- `document_chunk`
- `qa_record`
- `document`
- `knowledge_base`
- 当前知识库的 Redis RAG 问答缓存
- 本地上传文件

### 事务设计

数据库删除操作放在同一个事务中：

```text
删除 chunk -> 删除问答历史 -> 删除文档记录 -> 删除知识库记录
```

Redis 缓存清理和本地文件删除属于外部副作用，不受数据库事务回滚控制。因此系统通过事务提交后的回调执行：

```text
TransactionSynchronization.afterCommit()
```

这样可以避免数据库删除失败回滚，但本地文件已经被提前删除。

### 面试讲法

可以这样介绍：

```text
删除知识库不只是删主表，还要考虑文档、chunk、问答历史、Redis 缓存和本地文件。数据库相关删除放在一个事务里，保证业务数据一致。Redis 缓存和文件系统属于外部资源，我放到事务 afterCommit 回调里处理，避免数据库回滚但外部文件已经被删除的问题。
```

## 8. RAG 问答反馈闭环

### 背景

RAG 系统不能只返回答案，还需要收集用户对答案质量的反馈。反馈数据可以用于后续分析：

- 哪些知识库回答质量较差
- 哪些问题经常没有帮助
- 是检索召回问题，还是回答生成问题
- Prompt、切分策略、向量权重是否需要调整

### 当前能力

用户可以对问答历史提交反馈：

```text
1  -> 有帮助
-1 -> 没帮助
0/null -> 清除反馈
```

系统保存：

- `feedback_score`
- `feedback_note`
- `feedback_at`

仪表盘展示：

- 已反馈数量
- 有帮助数量
- 没帮助数量
- 有帮助占比

前端问答历史支持：

- 按问题或回答文本搜索
- 按反馈状态筛选
- 快速定位“没帮助”的回答做复盘

### 接口设计

```http
PUT /api/rag/history/{id}/feedback
```

请求体：

```json
{
  "feedbackScore": 1,
  "feedbackNote": "回答有帮助"
}
```

### 系统中的运行方式

1. 用户在回答卡片点击“有帮助”或“没帮助”。
2. 前端调用反馈接口。
3. 后端校验问答记录属于当前用户。
4. 后端保存反馈分数、备注和反馈时间。
5. 前端更新当前回答和历史列表状态。
6. 仪表盘统计反馈数据。

### 工程细节

清除反馈时需要把字段更新为 `null`。MyBatis-Plus 默认更新策略可能跳过 `null` 字段，所以这里不能简单依赖 `updateById`，而是使用 `LambdaUpdateWrapper#set` 显式更新：

```text
feedback_score = null
feedback_note = null
feedback_at = null
```

### 后续升级方向

- 增加反馈原因分类
- 对低质量回答自动进入复盘列表
- 基于反馈调整检索权重
- 区分“检索不准”和“回答组织不好”
- 导出问答反馈数据做离线评估

### 面试讲法

可以这样介绍：

```text
我给 RAG 问答加了反馈闭环。用户可以对回答标记有帮助或没帮助，系统保存反馈分数、备注和反馈时间，并在仪表盘统计反馈质量。这个模块为后续 Prompt 调优、检索权重调优和人工复盘提供数据基础。实现时还注意了 MyBatis-Plus 对 null 字段默认不更新的问题，清除反馈使用显式 update wrapper。
```
## 大模型接入：OpenAI-compatible Chat Completions

当前系统已经增加 `ChatModelService` 抽象，并提供 OpenAI-compatible 实现，默认模型配置为 DeepSeek `deepseek-v4-pro`。

它的作用是把 RAG 链路从“模板化回答”升级为“检索增强生成”：先用本地向量检索召回 chunk，再把问题和引用片段组织成 Prompt，交给真实大模型生成最终答案。

关键设计：

- `RagServiceImpl` 不直接依赖某个厂商 SDK，只依赖 `ChatModelService`。
- `OpenAiCompatibleChatModelService` 使用通用 Chat Completions 协议。
- `ChatModelProperties` 通过环境变量配置模型开关、base URL、API Key、模型名、超时时间和上下文长度。
- 没有配置 Key 或调用失败时，系统自动降级到本地模板化回答。
- Redis 问答缓存会加入回答模式命名空间，避免本地模板答案和大模型答案互相污染。

这种设计适合面试表达为“模型供应商解耦 + 可降级 RAG 架构”。

详细说明见：

```text
docs/大模型接入说明.md
```

## 9. 大模型调用可观测性

### 背景

真实大模型接入后，用户看到一个答案，并不能直接知道它到底来自哪里。实际项目里经常会出现这些情况：

- API Key 没配好，系统降级成了本地模板回答。
- Redis 命中了旧缓存，看起来像“模型没有更新”。
- 大模型接口超时或失败，但前端只显示普通答案。
- 问答耗时变慢，但没有字段可以定位问题。

所以系统需要把回答来源、模型名、耗时、缓存命中和降级状态显式记录下来。

### 当前能力

`RagAskResponse` 和 `QaRecordResponse` 已加入以下字段：

```text
answerSource  回答来源，MODEL / LOCAL_FALLBACK
modelName     实际调用的模型名
latencyMs     问答链路耗时，单位毫秒
cacheHit      是否命中 Redis 问答缓存
fallback      是否发生模型降级
```

这些字段会出现在普通问答、流式问答完成事件和历史记录中。`qa_record` 表也保存了回答来源、模型名、耗时和降级状态，便于后续做统计分析。

### 系统中的运作方式

1. 用户提交问题后，后端先执行 RAG 检索召回引用片段。
2. 如果 Redis 问答缓存命中，直接返回缓存答案，并标记 `cacheHit=true`。
3. 如果没有缓存，系统尝试调用 `ChatModelService`。
4. 模型返回成功时，标记 `answerSource=MODEL`，记录模型名和耗时。
5. 模型未启用或调用失败时，使用本地模板回答；如果是“已启用但调用失败”，额外标记 `fallback=true`。
6. 最终答案、引用片段和观测字段一起保存到问答历史。
7. 前端回答卡片展示“DeepSeek 生成 / 缓存命中 / 本地回答 / 模型降级”、模型名和耗时。

### 技术价值

- 提高可排查性：不用翻日志也能知道回答是否来自真实模型。
- 支持面试表达：体现工程化意识，而不是只会调 API。
- 方便后续扩展：可以继续统计平均耗时、成功率、降级次数、缓存命中率。

### 面试讲法

可以这样介绍：

```text
我给 RAG 问答链路加了可观测字段。每次回答都会记录来源、模型名、耗时、是否命中缓存、是否发生降级，并且这些信息会在前端和历史记录中展示。这样可以快速判断答案是 DeepSeek 生成的、Redis 缓存返回的，还是模型失败后本地降级的。这属于大模型应用里的工程化治理能力，为后续做监控和质量分析打基础。
```

## 10. 文本清洗与细粒度 Chunk 切分

### 背景

早期版本使用固定长度切分：每个 chunk 约 800 字，并保留 100 字 overlap。这个实现简单，但在引用来源展示时会有两个明显问题：

- chunk 太大，用户点击 `[1]` 后仍然需要在很长的片段里寻找具体依据。
- PDF / Word 提取文本时可能出现大量空行，空白内容会占用 chunk 长度，降低检索和阅读体验。

### 当前处理

`TextChunker` 已调整为“清洗空白 + 段落/句子优先切分”：

```text
原始文本
-> 统一换行符
-> 去除 BOM / 零宽字符
-> 压缩行内空格
-> 多个连续空行最多保留一个段落分隔
-> 优先按段落切分
-> 段落过长时按句号、问号、感叹号、分号等句子边界切分
-> 仍然过长时按最大长度硬切
```

当前参数：

```text
chunk_size   = 420
overlap_size = 60
```

### 系统中的作用

1. 用户上传文档后，解析任务先通过 `TextDocumentReader` 提取纯文本。
2. `TextChunker` 对文本进行空白清洗，减少无意义空行。
3. 切分时尽量保持段落和句子的完整性。
4. 新 chunk 写入 `document_chunk` 表，后续 RAG 检索和引用来源都基于这些 chunk。

### 注意事项

这个优化只影响后续重新解析生成的 chunk。已经解析过的旧文档仍然保留旧 chunk，需要在前端点击“解析/重新解析”后才会应用新的切分策略。

### 面试讲法

可以这样介绍：

```text
我没有只做固定字符长度切分，而是在 TextChunker 里加入了文本清洗和段落/句子优先的切分策略。系统会先清理 PDF、Word 提取文本时常见的多余空行和空格，再尽量按自然段和句子边界生成更小的 chunk。这样 RAG 检索的引用片段更短，用户点击引用编号后能更快定位答案依据。
```

## 11. RAG 检索调试面板

### 背景

RAG 回答不准确时，问题不一定出在大模型。常见原因包括：

- 文档没有解析成功。
- chunk 切分粒度不合适。
- 查询关键词没有命中。
- 向量相似度分数低。
- 召回片段正确，但模型回答组织不好。
- Redis 命中了旧答案。

因此系统需要一个不调用大模型的检索调试入口，用于单独观察召回链路。

### 当前能力

后端新增接口：

```text
POST /api/rag/debug
DELETE /api/rag/cache?kbId={kbId}
```

调试接口返回：

- 当前 `topK`
- 是否命中问答缓存
- 当前回答模式命名空间
- 检索耗时
- 查询词
- 每个召回 chunk 的文档名、chunk 编号、字数
- 向量分、关键词分、最终分
- 命中的关键词
- chunk 原文

前端问答区新增：

- “检索调试”按钮：只跑检索，不调用 DeepSeek。
- “清理问答缓存”按钮：清理当前知识库的 Redis 问答缓存。
- 调试面板：展示召回详情和高亮关键词。

### 系统中的运行方式

1. 用户输入问题。
2. 点击“检索调试”。
3. 后端校验当前用户是否拥有该知识库。
4. 调用 `VectorSearchService.search()` 执行原本的召回逻辑。
5. 返回每个 chunk 的分数、命中词和内容。
6. 前端展示调试结果，不产生问答历史，也不消耗大模型调用。

### 技术价值

- 可以快速判断回答问题是“检索问题”还是“生成问题”。
- 可以解释为什么某个 chunk 被召回。
- 可以排查 Redis 旧缓存导致的结果不更新。
- 面试时能体现 RAG 工程化调试能力。

### 面试讲法

可以这样介绍：

```text
我给 RAG 系统做了一个检索调试面板。它不会调用大模型，而是单独执行召回链路，展示 TopK chunk、向量分、关键词分、最终分和命中关键词。这样当回答不准时，可以先判断是文档解析、切分、召回排序还是模型生成的问题。同时我还提供了当前知识库的一键清理问答缓存能力，避免 Redis 旧答案干扰调试。
```

RAG 系统不能只写死一个 Prompt。不同使用场景对回答的要求不同：

- 工作查询希望回答严谨、引用明确。
- 快速问答希望内容短、直接。
- 面试准备希望回答结构化，能讲清楚工程意义和注意点。

如果所有场景共用一个 Prompt，系统要么太啰嗦，要么不够完整，也不方便后续运营调优。


2. 使用对应系统 Prompt 调用 DeepSeek。
3. 本地降级模板也按同样风格输出。

```text
-> Redis key 加入 __answer_style__
```

### 技术价值

- 把 Prompt 从“写死字符串”升级成可管理策略。
- 支持不同业务场景复用同一套 RAG 链路。
- 避免不同风格回答共用同一个 Redis 缓存。
- 面试时可以体现 Prompt Engineering 工程化能力。

### 面试讲法

可以这样介绍：

```text
我没有把 Prompt 写成单一固定模板，而是抽象了 AnswerStyle，支持严谨、简洁和面试讲解三种回答风格。前端选择风格后，后端会根据风格选择不同系统 Prompt，同时本地降级模板和 Redis 缓存 key 也会带上风格标识，避免不同回答策略互相污染缓存。这体现了 Prompt 工程化和可运营调优的思路。
```

## 13. 文档解析指标与任务可观测性

### 背景

文档解析不仅要知道成功或失败，还需要知道解析结果是否合理。例如：

- 一个大文档只切出 1 个 chunk，可能说明切分策略有问题。
- 一个小文档切出过多 chunk，可能说明清洗或切分过碎。
- 解析耗时过长，可能是 PDF / Word 读取成本高，或文档内容异常。

因此系统需要记录解析产物和耗时。

### 当前能力

`document` 表新增字段：

```text
chunk_count        本次解析生成的 chunk 数
parse_duration_ms 本次解析耗时，单位毫秒
```

解析成功时记录 chunk 数和耗时；解析失败时记录耗时并把 chunk 数置为 0。前端文档列表和解析任务中心都会展示这些指标。

### 系统中的运作方式

```text
DocumentParseTask 开始解析
-> 记录 startedAt
-> TextDocumentReader 提取文本
-> TextChunker 切分 chunk
-> 写入 document_chunk
-> document.chunk_count = chunks.size()
-> document.parse_duration_ms = elapsedMillis
```

重新解析时会先清空旧指标，避免解析中仍显示上一轮结果。

### 面试讲法

可以这样介绍：

```text
我给文档解析链路加了可观测指标。每次解析会记录生成的 chunk 数和解析耗时，并在文档列表和任务中心展示。这样如果回答效果不好，可以先从文档解析质量入手排查，比如 chunk 数是否异常、解析是否耗时过长，而不是直接猜测是大模型回答问题。
```

## 15. 后台任务日志与异步任务可观测性

### 背景

文档解析属于异步后台任务，用户点击“解析”后不会一直停留在请求链路里等待结果。如果只在控制台打印日志，用户和面试展示时都很难说明任务到底经历了哪些状态。

因此系统增加了 `task_log` 表，把任务生命周期中的关键事件持久化下来。

### 当前能力

`task_log` 表记录字段包括：

```text
user_id      当前用户
kb_id        知识库
document_id  文档
task_type    任务类型，例如 DOCUMENT_PARSE
status       STARTED / SUCCESS / FAILED
message      任务说明或失败原因
duration_ms  本次任务耗时
created_at   日志产生时间
```

当前文档解析任务会记录三类事件：

- `STARTED`：任务开始，记录正在解析的文档名。
- `SUCCESS`：解析完成，记录生成了多少个 chunk 和耗时。
- `FAILED`：解析失败，记录失败原因和耗时。

前端在“解析任务中心”中为每条任务增加“日志”按钮，可以查看该文档最近 30 条任务日志。

### 系统中的运作方式

```text
用户点击解析
-> 后端设置 document.status = PARSING
-> DocumentParseTask 异步执行
-> 写入 task_log: STARTED
-> 读取文档并切分 chunk
-> 成功：写入 task_log: SUCCESS，并更新 document.chunk_count / parse_duration_ms
-> 失败：写入 task_log: FAILED，并更新 document.error_msg / retry_count
-> 前端通过 /api/dashboard/tasks/{documentId}/logs 查询日志
```

### 技术价值

- 异步任务不再是黑盒，排查文档解析失败时可以直接看日志。
- 日志和业务数据分离，`document` 表保留当前状态，`task_log` 表保留历史过程。
- 适合后续扩展更多后台任务，例如向量化、批量重建索引、缓存预热、定时清理等。
- 面试时可以说明自己考虑了异步任务的可观测性，而不只是完成了功能闭环。

### 面试讲法

可以这样介绍：

```text
文档解析是异步任务，所以我没有只依赖接口返回或控制台日志，而是设计了 task_log 表记录任务生命周期。每次解析会记录 STARTED、SUCCESS、FAILED 三类事件，包含耗时、失败原因和文档归属。前端任务中心可以直接查看日志，这样用户上传文档后如果解析失败，可以在页面内定位原因。这体现了后台任务可观测性和排障体验。
```

## 17. 文档批量操作与整库索引重建

### 背景

知识库文档数量变多后，逐个点击解析或删除效率很低，也不利于演示后台任务体系。因此系统新增文档批量操作能力，把“批量重新解析”“批量删除”和“整库重建索引”接入现有文档管理页。

### 当前能力

新增接口：

```text
POST /api/doc/batch/parse
DELETE /api/doc/batch
POST /api/doc/kb/{kbId}/rebuild
```

批量解析会逐个复用单文档解析逻辑，继续使用分布式锁防止重复提交任务，并在提交前清理旧 chunk 和问答缓存。批量删除会逐个校验当前用户归属，删除文档、切片和本地文件，并清理对应知识库的 RAG 缓存。整库重建索引会查询当前知识库下的全部文档并批量提交解析任务。

### 系统中的运行方式

```text
用户勾选文档
-> 前端调用批量解析或批量删除接口
-> 后端逐个校验文档归属
-> 批量解析：提交异步解析任务，清理旧 chunk 和缓存
-> 批量删除：删除 document、document_chunk 和上传文件
-> 返回 total / submitted / deleted / skipped 汇总
-> 前端刷新文档列表并展示操作结果
```

### 技术价值

- 从单文档管理升级为批量管理，更接近真实知识库维护场景。
- 复用已有异步解析、分布式锁、任务日志和缓存清理逻辑，避免另起一套不一致流程。
- 整库重建索引为后续接入 Milvus、pgvector 或 Redis Vector Search 预留了自然入口。
- 批量接口返回汇总结果，前端可以展示成功和跳过数量，用户体验更可控。

### 面试讲法

可以这样介绍：

```text
我给文档管理补了批量操作能力，包括批量重新解析、批量删除和整库重建索引。实现时没有另写一套解析流程，而是复用已有单文档解析逻辑，所以分布式锁、异步任务、任务日志、chunk 清理和 Redis 缓存失效都能保持一致。批量接口会逐条处理并返回 submitted、deleted、skipped 等汇总信息，这样即使部分文档正在解析或失败次数过多，也不会影响其他文档继续处理。这体现了后台任务系统和知识库维护能力的完整性。
```

## 18. RAG 问答质量评估与低质量问题看板

### 背景

RAG 系统上线后，重点不只是“能回答”，还要能发现哪些回答质量差、哪些问题需要补充资料或调整参数。因此系统基于 `qa_record` 中已有的回答来源、引用数量、耗时、fallback 和用户反馈，新增质量评估看板。

### 当前能力

新增接口：

```text
GET /api/rag/quality/overview?kbId={kbId}
GET /api/rag/quality/issues?kbId={kbId}&type={type}&limit=20
```

质量总览统计最近 1000 条问答记录：

```text
totalCount        问答总数
feedbackCount     已反馈数量
helpfulCount      有帮助数量
unhelpfulCount    无帮助数量
modelAnswerCount  大模型回答数量
localAnswerCount  本地回答数量
fallbackCount     模型降级数量
noCitationCount   无引用回答数量
highLatencyCount  高耗时回答数量
averageLatencyMs  平均耗时
qualityScore      综合质量分
```

低质量列表支持筛选：

```text
ALL           问题记录
UNHELPFUL     低评分
FALLBACK      模型降级
NO_CITATION   无引用
HIGH_LATENCY  高耗时
NO_FEEDBACK   未反馈
```

### 系统中的运行方式

```text
用户打开 RAG 页
-> 前端加载当前知识库质量总览
-> 后端查询当前用户当前知识库最近 1000 条 qa_record
-> 统计反馈、fallback、无引用、高耗时和平均耗时
-> 前端展示质量分和低质量问题列表
-> 用户可按问题类型筛选，定位需要调参或补资料的问题
```

### 技术价值

- 把 RAG 从“功能闭环”推进到“质量闭环”。
- 低评分、fallback、无引用、高耗时都是可直接行动的问题信号。
- 可以指导后续优化：补文档、调 TopK、调检索权重、优化 Prompt、检查模型配置。
- 不新增复杂依赖，先复用已有问答历史数据，成本低但展示价值高。

### 面试讲法

可以这样介绍：

```text
我给 RAG 问答做了质量评估看板，不只是保存历史记录，而是基于 qa_record 统计低评分、模型降级、无引用和高耗时问题。前端可以按问题类型筛选低质量问答，用来反推是文档缺失、检索参数不合适、模型不可用，还是回答耗时过高。这样系统形成了从文档解析、检索问答、用户反馈到质量评估的闭环，后续可以继续接离线评测集和自动化 Prompt 优化。
```

## 19. 系统监控与运行健康检查

### 背景

RAG 系统接入了数据库、Redis、大模型、缓存、限流和异步任务等多个组件。功能跑通之后，需要一个面向排障和演示的监控入口，快速判断系统是否处于可用状态，以及当天问答链路是否稳定。

### 当前能力

新增接口：

```text
GET /api/dashboard/health
GET /api/dashboard/metrics/today
```

健康检查覆盖：

```text
MYSQL       通过 SELECT 1 检查数据库连接
REDIS       通过 PING 检查 Redis 连接
CHAT_MODEL  检查大模型开关和 API Key 配置
RAG_CACHE   展示问答缓存开关和 TTL
RATE_LIMIT  展示接口限流开关和问答限流规则
```

今日指标覆盖：

```text
qaCount            今日问答数
modelAnswerCount   今日大模型回答数
localAnswerCount   今日本地回答数
fallbackCount      今日模型降级次数
highLatencyCount   今日高耗时问答数
averageLatencyMs   今日平均问答耗时
modelSuccessRate   今日模型调用成功率估算
cacheEnabled       缓存是否启用
rateLimitEnabled   限流是否启用
```

### 系统中的运行方式

```text
用户打开 RAG 页
-> 前端调用 /api/dashboard/health
-> 后端轻量探测 MySQL、Redis 和配置状态
-> 前端调用 /api/dashboard/metrics/today
-> 后端从 qa_record 统计当天问答指标
-> 前端展示状态灯、组件说明和今日指标卡
```

健康检查不会主动请求外部大模型接口，只检查是否启用、是否配置 API Key、当前模型名和 baseUrl，避免产生额外费用或让监控依赖外部网络。

### 技术价值

- 可以快速定位 Redis、MySQL、大模型配置、缓存和限流是否异常。
- 今日指标能反映系统当前运行质量，例如 fallback 是否异常增多、耗时是否升高。
- 监控面板和前面的任务日志、质量评估形成可观测性闭环。
- 面试时可以讲清楚“功能完成后如何排障、如何判断系统稳定性”。

### 面试讲法

可以这样介绍：

```text
我给系统补了一个监控面板，后端提供 health 和 today metrics 两类接口。health 会轻量检查 MySQL、Redis、大模型配置、缓存和限流状态；today metrics 会基于 qa_record 统计当天问答数、模型回答数、fallback 次数、高耗时次数和平均耗时。这样当用户反馈问答变慢或模型不可用时，可以先从监控面板判断是 Redis、数据库、大模型配置还是问答链路本身的问题，体现了项目的可观测性和排障能力。
```

## 20. 真实 Embedding 模型接入与向量持久化

### 背景

前面的本地向量检索已经跑通了 RAG 问答闭环，但哈希向量更适合作为离线演示和兜底方案。真实系统需要把文档切片转换成语义向量，并在检索时复用已生成的向量，避免每次问答都重复计算文档向量。

### 当前能力

新增 OpenAI-compatible Embedding 接入，支持通过环境变量配置：

```text
EMBEDDING_MODEL_ENABLED
EMBEDDING_MODEL_BASE_URL
EMBEDDING_MODEL_ENDPOINT_PATH
EMBEDDING_MODEL_API_KEY
EMBEDDING_MODEL_NAME
EMBEDDING_MODEL_TIMEOUT_SECONDS
EMBEDDING_MODEL_DIMENSIONS
```

当 `EMBEDDING_MODEL_ENABLED=true` 且配置了 API Key 时，系统会调用兼容 `/v1/embeddings` 的向量模型。未启用或调用失败时，会自动回退到 `local-hash-v1`，保证开发环境和演示环境不依赖外部网络也能运行。

文档切片表新增字段：

```text
embedding_model  记录向量来源和维度
embedding_json   保存切片向量
```

解析文档时会立即生成并保存每个 chunk 的向量；问答检索时优先读取数据库里的 `embedding_json`，只有旧数据缺失向量、向量维度不匹配或 JSON 异常时，才临时重新计算。整库重建索引功能可以用于把历史切片批量补齐为新模型向量。

系统监控模块也新增了 `EMBEDDING_MODEL` 健康项，用于展示向量模型是未启用、缺少 API Key，还是已经具备调用条件。

### 系统中的运行方式

```text
上传文档 -> 文档解析任务切分 chunk
-> TextEmbeddingService 生成向量
-> 保存 chunk 内容、embedding_model 和 embedding_json
-> 用户提问时生成问题向量
-> 检索服务读取已保存的 chunk 向量计算相似度
-> 结合关键词得分、TopK 和用户偏好权重返回候选片段
```

### 技术价值

- 从“模拟向量检索”升级为可接真实 Embedding 服务的语义检索链路。
- 向量在解析阶段持久化，减少问答时重复计算文档向量的开销。
- 保留本地哈希兜底，开发、测试、答辩演示不被外部模型配置卡住。
- 为后续接入 pgvector、Milvus、Qdrant 或 Redis Vector Search 留出了清晰边界：只需要把当前本地扫描检索替换为向量库写入和召回。

### 面试讲法

可以这样介绍：

```text
项目最开始使用本地哈希向量完成 RAG 闭环，后续我把 Embedding 抽象成 TextEmbeddingService，并实现了 OpenAI-compatible 的真实向量模型接入。文档解析时会把每个 chunk 的向量持久化到 document_chunk 表，问答检索时优先复用已保存向量，只对问题实时生成向量，这样可以降低重复计算成本。同时保留 local-hash-v1 作为兜底，当模型未配置或调用失败时系统仍然可用。这个设计把向量模型和检索实现解耦，下一步接 pgvector、Milvus 或 Qdrant 时，可以沿用同一套解析和问答链路，只替换向量存储与召回层。
```
