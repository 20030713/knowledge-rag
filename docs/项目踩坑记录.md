# 企业知识库 RAG 问答系统：踩坑记录

这份文档专门记录开发过程中遇到的典型问题、真实原因、排查方式和最终解决方案。后续遇到新的坑，统一追加到这里。

## 1. 前端上传文档后提示「知识库不存在」

### 现象

在前端选择某个知识库后上传文档，请求 `/api/doc/upload` 返回 `200 OK`，但页面显示：

```text
知识库不存在
```

浏览器 Network 里可以看到请求已经发出，Authorization 也带了，后端也返回了 JSON 业务错误。

### 根因

后端使用 MyBatis-Plus 的 `ASSIGN_ID` 生成 Long 类型雪花 ID。这个 ID 通常是 19 位整数。

JavaScript 的 `number` 类型只能安全表示到：

```text
9007199254740991
```

超过这个范围后，前端会发生精度丢失。也就是说，后端返回的知识库 ID 到前端后已经被四舍五入，上传时传回后端的 `kbId` 不再是数据库里的真实 ID。

后端按错误的 `kbId + userId` 查询，自然查不到知识库，于是返回「知识库不存在」。

### 排查方式

1. 打开浏览器 DevTools。
2. 查看 `/api/kb` 返回的知识库 ID。
3. 查看 `/api/doc/upload` 表单里提交的 `kbId`。
4. 如果两个 ID 看起来相似但末尾不一致，基本就是 JS 大整数精度丢失。

### 解决方案

后端统一把 Long ID 序列化为字符串：

```java
@Configuration
public class JacksonConfig {

    @Bean
    public Jackson2ObjectMapperBuilderCustomizer longToStringCustomizer() {
        return builder -> builder
                .serializerByType(Long.class, ToStringSerializer.instance)
                .serializerByType(Long.TYPE, ToStringSerializer.instance);
    }
}
```

前端所有 ID 类型改成 `string`：

```ts
export type KnowledgeBase = {
  id: string;
  name: string;
};

export type DocumentItem = {
  id: string;
  kbId: string;
};
```

上传时直接传字符串 ID：

```ts
formData.set("kbId", kbId);
```

### 经验总结

只要后端使用 Java `Long` 雪花 ID，返回给前端时都建议转成字符串。尤其是用户 ID、订单 ID、知识库 ID、文档 ID 这类主键，不要让浏览器用 `number` 承接。

这是前后端联调里非常常见的问题，面试时也可以作为一个真实工程细节来讲。

## 2. 前端报 `Unexpected token 'I'`

### 现象

登录或请求接口时，前端控制台报：

```text
Unexpected token 'I', "Invalid CORS request" is not valid JSON
```

### 根因

后端 CORS 只放行了固定端口，例如：

```text
http://localhost:5173
```

但 Vite 当前端口被占用时会自动顺延，比如跑到：

```text
http://localhost:5175
```

Spring 拦截跨域请求后返回纯文本：

```text
Invalid CORS request
```

前端请求封装仍然按 JSON 解析响应，于是报 `Unexpected token 'I'`。

### 解决方案

后端开发环境放行本地端口段：

```java
registry.addMapping("/api/**")
        .allowedOriginPatterns("http://localhost:*", "http://127.0.0.1:*")
        .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
        .allowedHeaders("*")
        .allowCredentials(true);
```

前端请求封装先判断 `content-type`：

```ts
const contentType = response.headers.get("content-type") ?? "";
if (!contentType.includes("application/json")) {
  const message = await response.text();
  throw new Error(message || "请求失败，请检查后端服务或跨域配置");
}
```

### 经验总结

本地开发时，Vite 端口不一定固定。CORS 不要只写死一个端口；同时前端请求层不要默认所有响应都是 JSON。

## 3. 启动后端后数据库表没有自动创建

### 现象

前端点击进入工作台或注册登录时显示：

```text
系统异常
```

后端日志里出现：

```text
Unknown database 'knowledge_rag'
```

或表不存在相关错误。

### 根因

`sql/init.sql` 不会因为启动 Spring Boot 自动执行。它只会在 Docker MySQL 容器首次初始化数据目录时执行。

如果使用的是本地 MySQL，而不是 Docker 容器里的 MySQL，就不会自动跑 `sql/init.sql`。

### 解决方案

开发阶段可以用启动初始化器检查并创建当前阶段需要的表：

```java
@Component
public class DatabaseSchemaInitializer implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        createUserTable();
        createKnowledgeBaseTable();
        createDocumentTable();
    }
}
```

如果数据库本身也可能不存在，JDBC URL 需要加：

```text
createDatabaseIfNotExist=true
```

### 经验总结

要区分：

- Docker MySQL 首次初始化脚本：`sql/init.sql`
- Spring Boot 启动时自动建表：应用内部初始化逻辑
- 生产环境数据库迁移：Flyway / Liquibase 更合适

当前项目处于开发演示阶段，用启动初始化器可以提高本地体验。

## 4. 文档解析先支持哪些格式

### 背景

文档上传模块已经支持：

```text
pdf / doc / docx / md / txt
```

但进入解析阶段时，有三个选择：

- 先支持 TXT / Markdown
- 直接支持 PDF / Word / TXT / Markdown
- 使用 LangChain4j 文档加载器统一解析

### 当前选择

先支持：

```text
TXT / Markdown
```

### 原因

TXT / Markdown 解析稳定、实现快，能尽快打通：

```text
上传文档 -> 读取文本 -> 清洗文本 -> chunk 切分 -> 写入 document_chunk 表
```

PDF / Word 解析虽然演示效果更完整，但会引入 PDFBox / Apache POI，代码量和兼容性问题都会增加。当前阶段更重要的是尽快进入 RAG 主流程。

### 后续扩展

后续可以新增解析器接口，例如：

```java
public interface DocumentTextExtractor {
    boolean supports(String fileType);
    String extract(Path path);
}
```

然后分别实现：

- `PlainTextExtractor`
- `MarkdownExtractor`
- `PdfBoxExtractor`
- `PoiWordExtractor`

这样既能保持当前 MVP 简洁，也方便以后扩展 PDF / Word。

## 5. 中文 RAG 检索不能只按空格切词

### 背景

关键词检索版 RAG 先用于跑通主流程：

```text
用户问题 -> 检索 document_chunk -> 返回回答和引用片段
```

如果像英文一样只按空格拆分问题，中文问题经常会被当成一个完整长句，导致召回很差。

### 当前处理

当前检索会同时使用：

- 普通分隔符切出的词
- 中文连续二字片段

例如：

```text
项目核心功能
```

会额外产生：

```text
项目 / 目核 / 核心 / 心功 / 功能
```

这样可以在不引入中文分词库的情况下，提高 MVP 阶段的中文命中率。

### 后续扩展

后续接入向量检索后，这个问题会主要交给 Embedding 模型处理。关键词检索仍可保留为兜底召回或混合检索的一部分。

## 6. 前端记住密码只能用于本地演示

### 背景

登录页为了方便本地演示，会记住上一次登录的用户名。用户希望密码也能保留上一次输入值，避免每次重启或刷新都回到演示默认密码。

### 当前处理

前端新增“记住密码”选项：

- 默认不保存密码
- 用户主动勾选后，登录成功才保存
- 取消勾选并登录成功后，会清除本地保存的密码

### 注意点

当前实现使用浏览器 `localStorage` 保存演示密码，这只适合个人本地开发和项目演示。

真实生产系统不应该明文保存密码，通常应该依赖：

- 浏览器自带密码管理器
- 短期 token + refresh token
- 更严格的设备可信策略

## 7. 新增后端接口或表结构后，前端仍显示系统异常

### 背景

新增仪表盘接口后，前端 `RAG` 页显示：

```text
统计加载失败 / 系统异常
```

### 常见原因

后端代码已经修改，但浏览器连接的仍然是修改前启动的旧后端进程。

尤其是新增了：

- 新 Controller
- 新 Service
- 新表，例如 `qa_record`
- 新字段或新 Mapper

这些变化不会自动进入已经运行的 Spring Boot 进程，需要重启后端。

### 当前处理

仪表盘服务已经加了容错：如果问答历史统计暂时失败，不会拖垮整个仪表盘，基础统计仍然可以返回。

前端也把单纯的“系统异常”提示改成：

```text
统计接口异常，请重启后端后再刷新
```

### 经验总结

开发阶段遇到新增接口 500 时，优先检查：

1. 后端是否已经重启
2. 数据库表是否已经创建
3. 前端代理是否仍指向 `localhost:8080`
4. 后端日志中的真实 SQL / 映射异常

## 8. 给已有表新增字段时，不只要改 CREATE TABLE

### 背景

异步解析失败重试机制需要给 `document` 表新增：

```text
retry_count
```

如果只改 `CREATE TABLE IF NOT EXISTS document (...)`，已经存在的本地表不会自动多出这个字段。

### 当前处理

启动初始化器中新增了字段检查：

```text
information_schema.columns
```

如果字段不存在，再执行：

```sql
ALTER TABLE `document` ADD COLUMN `retry_count` INT NOT NULL DEFAULT 0
```

### 经验总结

开发阶段每次新增数据库字段，都要同时考虑：

- 新库初始化脚本 `sql/init.sql`
- Spring Boot 启动时的自动补表 / 补字段逻辑
- Java 实体字段
- DTO 返回字段
- 前端类型定义

只改其中一处，很容易出现“本地旧库启动后接口系统异常”的问题。

## 9. Hashing 向量不等于真正的大模型 Embedding

### 背景

系统新增了本地 Embedding 与向量检索模块，使用 Hashing Vectorizer 生成固定维度向量，再用余弦相似度召回 chunk。

### 容易误解的点

Hashing Vectorizer 虽然能生成“向量”，但它不是大模型 Embedding。

它主要基于 token 的 hash 分布来表达文本，优点是：

- 不需要外部 API
- 不需要训练模型
- 不需要安装向量数据库
- 本地演示稳定
- 方便先搭好向量检索架构

但它的缺点也很明确：

- 不能真正理解复杂语义
- 同义词召回能力有限
- 仍然比较依赖文本表面特征
- 效果不如真实 Embedding 模型

### 当前系统为什么仍然使用它

当前项目处于本地演示和实习项目完善阶段，优先目标是：

```text
先搭出完整 RAG 架构 -> 再逐步替换核心能力
```

因此当前使用本地 Hashing 向量作为轻量实现，让系统先具备：

- Embedding 接口抽象
- 向量检索服务抽象
- Top K 召回流程
- 引用片段返回
- 后续替换 Milvus / pgvector 的结构基础

### 经验总结

项目介绍时要讲清楚：

```text
当前是本地轻量向量检索实现，不是最终语义 Embedding。它的价值是先完成向量检索架构，后续可以替换为真实 Embedding 模型和向量数据库。
```

## 10. 上传支持的格式和解析支持的格式要一致

### 背景

早期上传接口允许：

```text
pdf / doc / docx / md / txt
```

但解析器只支持：

```text
txt / md
```

这样会导致用户看到“文件上传成功”，点击解析时才失败，体验上会觉得系统不完整。

### 根因

上传校验只关注文件后缀和保存，解析阶段才真正读取文件内容。两者如果维护在不同位置，就容易出现支持范围不一致。

### 当前处理

文档读取器已经扩展到：

```text
txt / md / pdf / docx / doc
```

对应技术：

- TXT / Markdown：`Files.readString`
- PDF：Apache PDFBox
- DOCX：Apache POI `XWPFDocument`
- DOC：Apache POI `HWPFDocument`

### 经验总结

只要新增一种上传格式，就要同时检查：

- 上传白名单
- 文档读取器
- 错误提示文案
- 前端 accept 列表
- README 和项目文档

上传能成功不代表 RAG 能处理，真正进入问答链路必须完成“保存文件 -> 解析文本 -> 切分 chunk -> 检索召回”整条链。

## 11. 删除主表时不要留下孤儿数据

### 背景

知识库删除如果只执行：

```sql
DELETE FROM knowledge_base WHERE id = ?
```

那么这个知识库下面的文档、chunk、问答历史、本地上传文件和 Redis 缓存都还会留在系统里。

### 当前处理

删除知识库时会级联清理：

- 文档切片
- 问答历史
- 文档记录
- 知识库记录
- Redis 问答缓存
- 本地上传文件

### 关键细节

数据库删除可以放在事务里，但文件系统和 Redis 不会跟着数据库事务自动回滚。

因此当前系统把 Redis 清理和文件删除放在事务提交后执行：

```text
TransactionSynchronization.afterCommit()
```

### 经验总结

涉及“数据库 + Redis + 本地文件”的删除操作，要区分：

- 数据库事务内应该完成的数据一致性
- 事务提交后才能执行的外部副作用
- 外部副作用失败时的日志和后续补偿策略

这类问题是项目从 Demo 走向工程化时很常见的坑。

## 12. MyBatis-Plus `updateById` 不一定会更新 null 字段

### 背景

问答反馈支持“清除反馈”，也就是把：

```text
feedback_score
feedback_note
feedback_at
```

重新置空。

### 坑点

如果直接这样写：

```java
record.setFeedbackScore(null);
record.setFeedbackNote(null);
record.setFeedbackAt(null);
qaRecordMapper.updateById(record);
```

MyBatis-Plus 默认字段更新策略可能会跳过 `null` 字段，导致数据库里的旧反馈没有被清除。

### 当前处理

使用 `LambdaUpdateWrapper#set` 显式更新：

```java
qaRecordMapper.update(new LambdaUpdateWrapper<QaRecord>()
        .eq(QaRecord::getId, record.getId())
        .set(QaRecord::getFeedbackScore, null)
        .set(QaRecord::getFeedbackNote, null)
        .set(QaRecord::getFeedbackAt, null));
```

### 经验总结

当业务语义需要“把字段清空”时，要特别注意 ORM 的 null 更新策略。不要只看 Java 对象字段变成了 null，还要确认 SQL 是否真的包含对应字段。

## 13. 调整切分策略后，旧文档不会自动重新切片

### 背景

系统把文档解析结果持久化到了 `document_chunk` 表。RAG 问答和引用来源展示都读取这个表，而不是每次提问都重新读取原始文件。

### 坑点

如果后续修改了 `TextChunker` 的切分参数或清洗策略，例如：

- 把 chunk 从 800 字改成 420 字
- 增加多余空行清洗
- 改成段落/句子优先切分

已经解析过的旧文档不会自动变化，因为数据库里保存的旧 chunk 仍然存在。

### 当前处理

文档重新解析时，系统会先删除该文档旧的 chunk，再按新的切分策略生成新 chunk：

```text
点击解析/重新解析 -> 删除旧 document_chunk -> 读取原文 -> 新 TextChunker 切分 -> 写入新 chunk
```

同时会清理当前知识库的 RAG 问答缓存，避免旧 chunk 生成的答案继续命中 Redis。

### 经验总结

凡是“解析后持久化”的处理链路，修改算法后都要考虑历史数据是否需要重算。对于本项目来说，切分策略变更后，需要对已有文档重新解析，才能看到新的 chunk 粒度和引用来源效果。

## 14. 回答风格切换后，Redis 缓存必须按风格隔离

### 背景

系统支持严谨模式、简洁模式、面试讲解模式。相同问题在不同风格下会生成不同答案。

### 坑点

如果 Redis 问答缓存 key 只包含：

```text
userId + kbId + question + model
```

那么用户先用“简洁模式”提问并缓存答案后，再切到“面试讲解模式”问同一个问题，系统可能直接返回简洁模式的旧答案，看起来像 Prompt 风格没有生效。

### 当前处理

缓存问题文本里加入回答风格命名空间：

```text
__answer_mode__:openai-compatible:{baseUrl}:{model}
__answer_style__:strict / brief / interview
```

这样相同问题在不同回答风格下会形成不同缓存 key。

### 经验总结

凡是会影响最终答案的参数，都应该参与缓存 key。RAG 系统里不仅问题文本会影响答案，模型、Prompt、回答风格、检索参数也可能影响答案，因此缓存设计要跟生成策略一起演进。

## 15. 同一个问题多种回答风格时，历史回填不能只按问题匹配

### 背景

前端在流式问答完成后，会重新加载问答历史，并尝试把刚生成的回答替换成带 `id` 的历史记录，方便用户继续做反馈。

### 坑点

如果只按问题文本匹配历史记录：

```text
record.question == currentQuestion
```

那么同一个问题分别用“简洁模式”“严谨模式”“面试讲解模式”回答过之后，前端可能把其他风格的历史记录回填到当前回答上。

表现就是：

```text
用户切到简洁模式 -> 提问 -> 历史回填命中了其他模式的同问题记录 -> 页面看起来又弹回其他模式
```

### 当前处理

历史回填时同时匹配：

```text
question + answerStyle
```

点击历史记录时，也同步设置当前回答风格选择器：

```text
setAnswer(record)
setQuestion(record.question)
setAnswerStyle(record.answerStyle)
```

### 经验总结

当一个业务对象的唯一性不只由一个字段决定时，前端回显和后端缓存都要使用同一套“业务维度”。本项目里，问答结果至少由 `question + kbId + answerStyle + model` 共同决定，不能只按问题文本匹配。
