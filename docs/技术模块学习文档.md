# 企业知识库 RAG 问答系统技术模块学习文档

本文档用于学习当前项目中各个功能模块的技术组成、模块职责、代码落点、运行链路和跑通方式。文档只说明技术实现，不包含面试讲法。

## 1. 系统整体架构

本项目是一个前后端分离的企业知识库 RAG 问答系统。

整体技术栈：

- 后端：Spring Boot 3.3.5、Java 21、MyBatis-Plus、MySQL、Redis、pgvector、JWT、Knife4j、PDFBox、Apache POI。
- 前端：React 18、TypeScript、Vite、lucide-react、原生 CSS。
- 存储：MySQL 保存业务数据，Redis 保存缓存、限流、进度、黑名单、热点问题等临时数据，pgvector 保存向量索引，文件上传后保存到本地或 Docker volume。
- AI 能力：兼容 OpenAI 协议的 Chat API 和 Embedding API，可接 DeepSeek、阿里云百炼千问 Embedding 等兼容接口。
- 部署：Docker Compose 编排 MySQL、Redis、pgvector、后端和前端。

核心请求流程：

```text
用户登录
  -> 创建知识库
  -> 上传文档
  -> 文档进入解析队列
  -> 后台任务读取文件并抽取文本
  -> TextChunker 切片
  -> Embedding 服务生成向量
  -> 切片写入 MySQL，向量写入 pgvector 或本地回退
  -> 用户提问
  -> 向量检索 + 关键词混合排序
  -> 拼接引用上下文
  -> 调用大模型或本地模板兜底
  -> 返回答案、引用、历史记录、缓存结果
```

### 4.2 pgvector

pgvector 使用 PostgreSQL 扩展保存高维向量。

配置位置：

```yaml
app:
  vector-store:
    pgvector:
      enabled: ${PGVECTOR_ENABLED:false}
      url: ${PGVECTOR_URL:jdbc:postgresql://localhost:5432/knowledge_vectors}
      username: ${PGVECTOR_USERNAME:postgres}
      password: ${PGVECTOR_PASSWORD:postgres}
      dimensions: ${PGVECTOR_DIMENSIONS:1024}
```

代码位置：

- `com.rag.knowledge.config.PgVectorProperties`
- `com.rag.knowledge.vector.PgVectorStoreService`
- `com.rag.knowledge.vector.PgVectorSearchService`
- `com.rag.knowledge.vector.RoutingVectorSearchService`

模块逻辑：

1. 文档解析后，每个 chunk 会生成 embedding。
2. `DocumentChunk` 写入 MySQL。
3. `PgVectorStoreService.upsert` 将 chunk id 和 embedding 写入 pgvector 表。
4. 用户提问时，`PgVectorSearchService` 将问题转成向量。
5. SQL 使用 `<=>` 计算向量距离，并按距离返回候选 chunk。
6. 候选结果再结合关键词分数做混合排序。

如果 pgvector 未启用或不可用，`RoutingVectorSearchService` 会自动回退到 `LocalVectorSearchService`。

### 5.1 RAG 答案缓存

代码位置：

- `com.rag.knowledge.service.RagAnswerCacheService`
- `com.rag.knowledge.service.impl.RedisRagAnswerCacheServiceImpl`

作用：

- 缓存用户对某个知识库、某个问题、某组 RAG 参数下的答案。
- 命中缓存后可以跳过向量检索、大模型调用和答案生成。
- 文档上传、删除、重新解析或清理缓存时，会按知识库维度删除相关缓存。

缓存 key 会结合：

- 用户 ID。
- 知识库 ID。
- 问题内容。
- 回答风格。
- TopK。
- 向量权重。
- 关键词权重。
- 大模型是否启用。
- Prompt 模板版本。
- 模型命名空间。

这样可以避免不同参数下的答案互相污染。

### 5.2 接口限流

代码位置：

- `com.rag.knowledge.service.RateLimitService`
- `com.rag.knowledge.service.impl.RedisRateLimitServiceImpl`

作用：

- 登录接口限制固定时间窗口内尝试次数。
- RAG 提问接口限制短时间内高频请求。

配置：

```yaml
app:
  rate-limit:
    enabled: true
    login:
      limit: 10
      window-seconds: 60
    rag-ask:
      limit: 20
      window-seconds: 60
```

实现方式：

- Redis 中对限流 key 做自增。
- 第一次写入时设置过期时间。
- 超过阈值后抛出业务异常。

### 5.3 Token 黑名单

代码位置：

- `com.rag.knowledge.service.TokenBlacklistService`
- `com.rag.knowledge.service.impl.RedisTokenBlacklistServiceImpl`

作用：

- 用户退出登录时，将当前 token hash 写入 Redis 黑名单。
- 拦截器解析 token 后会检查黑名单。
- 黑名单 key 设置 TTL，通常与 JWT 剩余有效期一致。

如果 Redis 不可用，代码中还有本地 `ConcurrentHashMap` 作为短期兜底。

### 5.4 文档解析进度

代码位置：

- `com.rag.knowledge.service.DocumentParseProgressService`
- `com.rag.knowledge.service.impl.RedisDocumentParseProgressServiceImpl`

作用：

- 保存文档解析过程中的阶段、进度百分比、已处理切片数、总切片数和提示信息。

典型阶段：

- `QUEUED`：已进入队列。

- `EMBEDDING`：生成向量。

作用：

- 用户每次提问后，将问题写入 Redis 统计。

### 5.6 分布式锁

代码位置：

- `com.rag.knowledge.service.DistributedLockService`
- `com.rag.knowledge.service.impl.RedisDistributedLockServiceImpl`

作用：

## 6. 认证与权限模块

### 6.1 用户认证

代码位置：

- `com.rag.knowledge.controller.AuthController`
- `com.rag.knowledge.service.AuthService`
- `com.rag.knowledge.service.impl.AuthServiceImpl`
- `com.rag.knowledge.security.JwtService`
- `com.rag.knowledge.interceptor.AuthInterceptor`
- `com.rag.knowledge.security.UserContext`

主要技术：

- JWT：登录后返回 token。
- BCrypt：保存密码时进行不可逆加密。
- Spring MVC Interceptor：请求进入 Controller 前校验 token。
- ThreadLocal：`UserContext` 保存当前请求的登录用户。

流程：

```text
注册
  -> 校验用户名和密码
  -> BCrypt 加密密码
  -> 写入 user 表

登录
  -> 校验账号密码
  -> 生成 JWT
  -> 写入登录日志
  -> 返回 token

请求业务接口
  -> AuthInterceptor 读取 Authorization header
  -> JwtService 解析 token
  -> 检查 token 黑名单
  -> UserContext 写入当前用户
  -> Controller/Service 读取当前用户
```

## 8. 文档管理与解析模块

### 8.1 文档上传

代码位置：

- `com.rag.knowledge.controller.DocumentController`
- `com.rag.knowledge.service.DocumentService`
- `com.rag.knowledge.service.impl.DocumentServiceImpl`
- `com.rag.knowledge.config.UploadProperties`

支持格式：

- `txt`
- `md`
- `pdf`
- `doc`
- `docx`

上传逻辑：

1. 校验知识库编辑权限。
2. 校验文件是否为空、后缀是否合法。
3. 清理原始文件名。
4. 根据知识库 ID、日期和 UUID 生成相对路径。
5. 使用 `MultipartFile.transferTo` 保存到上传目录。
6. 在 MySQL `document` 表中写入文档元数据。
7. 清理该知识库的 RAG 答案缓存。

文件内容本身不直接存入数据库，数据库保存的是文件元信息和相对路径。

### 8.2 文本抽取

代码位置：

- `com.rag.knowledge.storage.TextDocumentReader`

不同格式处理方式：

- TXT/Markdown：使用 `Files.readString` 按 UTF-8 读取。
- PDF：使用 PDFBox 的 `Loader.loadPDF` 和 `PDFTextStripper` 抽取文本。
- DOCX：使用 Apache POI 的 `XWPFDocument` 和 `XWPFWordExtractor`。
- DOC：使用 Apache POI 的 `HWPFDocument` 和 `WordExtractor`。

如果文件无法解析，会抛出业务异常并将文档状态标记为 `FAILED`。

### 8.3 文本切片

代码位置：

- `com.rag.knowledge.rag.TextChunker`

切片参数：

- `CHUNK_SIZE = 420`
- `OVERLAP_SIZE = 60`
- `MIN_BREAK_SIZE = 180`

处理流程：

1. 清理 BOM、零宽字符、重复空白、异常换行。
2. 按段落切分。
3. 长段落按中文/英文标点切成句子。
4. 累积句子直到接近 chunk 大小。
5. 每个 chunk 之间保留一定 overlap，减少上下文割裂。
6. 超长句子按合适断点硬切。

### 8.4 后台解析队列

代码位置：

- `com.rag.knowledge.service.DocumentTaskQueueService`
- `com.rag.knowledge.service.impl.DocumentTaskQueueServiceImpl`
- `com.rag.knowledge.job.DocumentTaskQueueWorker`
- `com.rag.knowledge.job.DocumentParseTask`
- `com.rag.knowledge.repository.TaskLogMapper`

运行方式：

1. 用户点击“解析”。
2. `DocumentServiceImpl.parse` 将文档状态改为 `PARSING`。
3. 删除旧 chunk 和旧向量。
4. 写入任务队列表。
5. `DocumentTaskQueueWorker` 每 2 秒扫描待处理任务。
6. 任务被抢占后状态改为 `RUNNING`。
7. 调用 `DocumentParseTask.parseQueued` 执行真正解析。
8. 成功后任务状态为 `DONE`，文档状态为 `COMPLETED`。
9. 失败后任务重试，最多 3 次。

队列消费批量大小：

```java
private static final int BATCH_SIZE = 2;
private static final int MAX_RETRY_COUNT = 3;
```

这个模块没有引入 Kafka 或 RabbitMQ，而是使用 MySQL 表模拟轻量任务队列。

### 8.5 切片与向量写入

文档解析任务中每个 chunk 会：

1. 调用 `TextEmbeddingService.embed(content)` 生成向量。
2. 构造 `DocumentChunk`。
3. 将 chunk 内容、字符数、embedding JSON、模型名写入 MySQL。
4. 调用 `VectorStoreService.upsert(chunk, embedding)` 写入 pgvector。

即使 pgvector 不启用，MySQL 中仍然保存 chunk 和 embedding JSON，因此本地回退检索可以继续运行。

## 9. Embedding 与向量检索模块

### 9.1 Embedding 服务

接口：

- `TextEmbeddingService`

实现：

- `OpenAiCompatibleTextEmbeddingService`
- `HashingTextEmbeddingService`

`OpenAiCompatibleTextEmbeddingService` 是主实现，支持兼容 OpenAI 协议的 embedding 服务。

请求体结构：

```json
{
  "model": "text-embedding-v4",
  "input": "chunk 文本",
  "dimensions": 1024
}
```

调用成功后：

1. 读取返回的 embedding 数组。
2. 转成 `double[]`。
3. 做 L2 normalize。
4. 返回给解析任务或检索任务。

调用失败或未配置时：

- 自动使用 `HashingTextEmbeddingService`。
- hashing embedding 不需要外部 API。
- 适合本地演示和兜底。

### 9.2 本地向量检索

代码位置：

- `com.rag.knowledge.vector.LocalVectorSearchService`

作用：

- 从 MySQL 读取候选 chunk。
- 读取 chunk 中保存的 embedding JSON。
- 对用户问题生成 embedding。
- 计算相似度。
- 再结合关键词分数排序。

适用场景：

- 没有启动 pgvector。
- pgvector 连接失败。
- pgvector 表中暂时没有数据。

### 9.3 pgvector 检索

代码位置：

- `com.rag.knowledge.vector.PgVectorSearchService`

核心 SQL：

```sql
SELECT chunk_id, 1 - (embedding <=> ?::vector) AS vector_score
FROM document_chunk_vector
WHERE user_id = ? AND kb_id = ?
ORDER BY embedding <=> ?::vector
LIMIT ?
```

说明：

- `<=>` 是 pgvector 的向量距离操作符。
- `1 - distance` 被转换成相似度分数。
- 先用向量召回候选，再加载 MySQL chunk 内容进行关键词混合排序。

### 9.4 路由检索

代码位置：

- `com.rag.knowledge.vector.RoutingVectorSearchService`

逻辑：

```text
如果 pgvector 可用
  -> 先查 pgvector
  -> 有结果则返回
否则
  -> 回退到 LocalVectorSearchService
```

这样系统可以在没有向量库的情况下正常演示，也可以在生产环境接入 pgvector 获得更好的检索性能。

### 10.1 普通问答流程

`RagServiceImpl.ask` 处理普通非流式问答。

流程：

1. 从 `UserContext` 获取当前用户。
2. 校验知识库读取权限。
3. 创建或获取当前对话 session。
4. 加载最近几轮对话作为 memory。
5. 根据用户偏好和请求参数计算 RAG 运行参数。
6. 查找当前回答风格对应的 Prompt 模板。
7. 生成缓存 key 并尝试读取 Redis 缓存。
8. 调用向量检索。
9. 对结果进行 rerank。
10. 组装引用列表。
11. 如果大模型启用，调用 `ChatModelService.generateAnswer`。
12. 如果大模型不可用，使用本地模板生成兜底答案。
13. 保存问答记录和引用记录。
14. 保存对话消息。
15. 记录热点问题。
16. 写入 Redis 缓存。

### 10.2 流式问答

`RagServiceImpl.streamAsk` 处理流式问答。

相关接口：

- 后端：`RagController` 中的 stream API。
- 前端：`api.streamAskRag`。
- UI：`ChatStage` 中实时拼接答案。

流程：

1. 先完成检索。
2. 先把引用列表推给前端。
3. 调用大模型流式接口。
4. 每收到一个 delta，就通过回调推送给前端。
5. 如果大模型不可用，后端将本地模板答案拆成小段模拟流式输出。
6. 最后发送完整 answer 作为 complete 事件。

### 10.3 引用溯源

每次回答都会生成 citations。

引用信息包括：

- 文档 ID。
- 文档名。
- chunk ID。
- chunk 编号。
- chunk 内容。
- 综合得分。
- 向量得分。
- 关键词得分。

前端会把答案里的 `[1]`、`[2]` 渲染成可点击按钮，点击后定位到对应引用 chunk。

### 10.4 检索调试

接口：

- `RagServiceImpl.debug`
- 前端 `api.debugRag`

作用：

- 不生成答案，只展示检索阶段命中的 chunk。
- 返回每个 chunk 的向量得分、关键词得分、最终得分、命中关键词。
- 用来观察“为什么系统认为这些片段相关”。

这个功能适合调试文档切片质量、关键词命中情况、向量模型效果和权重配置。

## 11. 大模型模块

接口：

- `ChatModelService`

实现：

- `OpenAiCompatibleChatModelService`

支持能力：

- 普通 JSON 响应。
- SSE 流式响应。
- 自定义 system prompt。
- 按回答风格生成不同 Prompt。
- 模型不可用时自动返回 `Optional.empty()`，由 RAG 服务兜底。

流式调用技术：

- 使用 JDK `HttpClient` 发送请求。
- 请求头 `Accept: text/event-stream`。
- 按行读取响应。
- 解析 `data:` 开头的 SSE 数据。
- 遇到 `[DONE]` 结束。
- 从 chunk JSON 中提取 delta 内容。

Prompt 输入由两部分组成：

1. system prompt：约束回答必须基于引用片段。
2. user prompt：包含用户问题和检索到的引用片段。

## 21. 常见运行现象说明

### 21.1 大模型不可用但仍能回答

原因：

- `CHAT_MODEL_ENABLED=false`。
- API Key 没配置。
- 模型接口调用失败。

系统行为：

- RAG 检索仍然执行。
- 答案由本地模板根据引用片段生成。
- `answerSource` 会显示为本地兜底。

### 21.2 Embedding 不可用但仍能解析和检索

原因：

- `EMBEDDING_MODEL_ENABLED=false`。
- API Key 没配置。
- Embedding 接口调用失败。

系统行为：

- 使用 `HashingTextEmbeddingService` 生成本地向量。
- 可以跑通切片、检索和问答。
- 向量效果不如真实 Embedding，但适合本地演示。

### 21.3 pgvector 不可用但仍能检索

原因：

- `PGVECTOR_ENABLED=false`。
- PostgreSQL 容器未启动。
- 维度配置不一致。
- 表未初始化。

系统行为：

- `RoutingVectorSearchService` 会回退到 `LocalVectorSearchService`。
- 检索仍然可用。
- 监控或向量索引页面会提示本地回退。

### 21.4 Redis 找不到数据

可能原因：

- 缓存有 TTL，过期后自动消失。
- 只在提问命中缓存逻辑后才会写入 RAG 缓存。
- 文档上传、删除、解析会主动清理知识库缓存。
- 有些 Redis 数据是短期状态，例如限流计数、解析进度、token 黑名单。

可以用以下命令查看 key：

```bash
docker exec -it knowledge-rag-redis redis-cli
KEYS *
```

## 23. 项目包结构说明

这一节按包名解释每个包的职责。包结构是理解 Spring Boot 项目分层的关键。

### 23.1 `com.rag.knowledge`

根包，包含项目启动类 `KnowledgeRagApplication`。

主要职责：

- 启动 Spring Boot 应用。
- 配置 `@MapperScan` 扫描 MyBatis Mapper。
- 启用配置属性绑定。
- 作为所有业务包的统一父包，方便 Spring 组件扫描。

### 23.2 `com.rag.knowledge.config`

配置包。

主要职责：

- 保存项目运行配置类。
- 把 `application.yml` 中的配置绑定成 Java 对象。
- 配置 Web、CORS、上传文件、密码加密、异步线程池、JSON 序列化、OpenAPI 文档等基础能力。

典型代码：

- `AuthProperties`：JWT 相关配置。
- `UploadProperties`：上传目录和大小限制。
- `ChatModelProperties`：大模型配置。
- `EmbeddingModelProperties`：Embedding 模型配置。
- `PgVectorProperties`：pgvector 配置。
- `VectorSearchProperties`：向量检索权重和 TopK 配置。
- `RagCacheProperties`：RAG 缓存配置。
- `RateLimitProperties`：限流配置。
- `CorsConfig`、`WebMvcConfig`：Web 层配置。
- `AsyncConfig`：异步任务线程池配置。
- `PasswordConfig`：密码编码器配置。
- `OpenApiConfig`：接口文档配置。

### 23.3 `com.rag.knowledge.controller`

控制器包，也就是接口入口层。

主要职责：

- 接收前端 HTTP 请求。
- 做参数校验。
- 调用 Service 层。
- 返回 DTO 响应。

这个包不应该写复杂业务逻辑，复杂业务应该放到 `service.impl`。

典型代码：

- `AuthController`：登录注册。
- `KnowledgeBaseController`：知识库管理。
- `DocumentController`：文档管理。
- `RagController`：RAG 问答。
- `PromptTemplateController`：Prompt 模板。
- `UserPreferenceController`：用户偏好。
- `RagEvalController`：RAG 评测。
- `DashboardController`：任务中心和系统监控。
- `AdminController`：管理后台。
- `HealthController`：健康检查。

### 23.4 `com.rag.knowledge.service`

业务接口包。

主要职责：

- 定义业务能力接口。
- 让 Controller 依赖接口，而不是直接依赖实现类。
- 让业务模块边界更清楚。

典型代码：

- `AuthService`
- `KnowledgeBaseService`
- `DocumentService`
- `RagService`
- `DashboardService`
- `AdminService`
- `PromptTemplateService`
- `UserPreferenceService`
- `RagEvalService`
- `RateLimitService`
- `RagAnswerCacheService`
- `DistributedLockService`

### 23.5 `com.rag.knowledge.service.impl`

业务实现包。

主要职责：

- 实现 `service` 包中定义的接口。
- 编排 Mapper、Redis、向量服务、大模型服务、权限服务等多个组件。
- 处理事务、权限、缓存清理、状态变更等核心业务。

典型代码：

- `AuthServiceImpl`：注册登录、密码校验、登录日志。
- `KnowledgeBaseServiceImpl`：知识库增删改查、成员管理、导入导出。
- `DocumentServiceImpl`：上传、解析入队、切片、索引状态。
- `RagServiceImpl`：检索、生成答案、流式输出、引用、历史、缓存。
- `DashboardServiceImpl`：任务中心、监控、诊断。
- `AdminServiceImpl`：用户管理、密码重置、审计日志。
- `RedisRagAnswerCacheServiceImpl`：Redis 答案缓存。
- `RedisRateLimitServiceImpl`：Redis 限流。
- `RedisTokenBlacklistServiceImpl`：Redis token 黑名单。
- `RedisDistributedLockServiceImpl`：Redis 分布式锁。

### 23.6 `com.rag.knowledge.repository`

数据访问包。

主要职责：

- 存放 MyBatis-Plus Mapper。
- 每个 Mapper 对应一个或一类数据库表。
- Service 通过 Mapper 读写 MySQL。

典型代码：

- `UserMapper`
- `KnowledgeBaseMapper`
- `KnowledgeBaseMemberMapper`
- `DocumentMapper`
- `DocumentChunkMapper`

### 23.7 `com.rag.knowledge.domain.entity`

数据库实体包。

主要职责：

```text

  -> 解析 JWT

  -> 写入 UserContext
  -> 放行 Controller
```
