# 大模型接入说明

## 模块目标

本模块把系统的问答链路从“检索片段后模板化整理”升级为“检索增强生成”。

当前流程：

1. 用户在前端提交问题。
2. 后端根据当前用户和知识库进行权限校验。
3. `VectorSearchService` 召回相关 chunk。
4. `RagServiceImpl` 将问题和引用片段组织成 Prompt。
5. `ChatModelService` 调用真实大模型生成答案。
6. 保存问答记录，并把完整 `RagAskResponse` 写入 Redis 问答缓存。

如果没有配置 API Key，或者模型接口调用失败，系统会自动降级到本地模板化回答，避免问答功能整体不可用。

## 技术选型

当前实现采用 OpenAI-compatible Chat Completions 接口，而不是直接绑定某一个厂商 SDK。当前默认配置已切换为 DeepSeek `deepseek-v4-pro`。

优点：

- 兼容 OpenAI、DashScope 兼容模式、智谱兼容模式、Ollama `/v1` 兼容接口。
- 换模型只需要改 `base-url`、`api-key`、`model`。
- 不额外引入厂商 SDK，减少依赖和版本冲突。
- 架构上通过接口抽象隔离模型供应商，便于面试讲解。

代价：

- 只能使用兼容接口的通用能力。
- 如果要用某厂商高级能力，例如函数调用、联网搜索、文件理解，需要后续扩展专门实现类。

## 配置项

```yaml
app:
  chat-model:
    enabled: ${CHAT_MODEL_ENABLED:false}
    base-url: ${CHAT_MODEL_BASE_URL:https://api.deepseek.com}
    endpoint-path: ${CHAT_MODEL_ENDPOINT_PATH:/v1/chat/completions}
    api-key: ${CHAT_MODEL_API_KEY:}
    model: ${CHAT_MODEL_NAME:deepseek-v4-pro}
    timeout-seconds: ${CHAT_MODEL_TIMEOUT_SECONDS:30}
    max-context-chars: ${CHAT_MODEL_MAX_CONTEXT_CHARS:6000}
    temperature: ${CHAT_MODEL_TEMPERATURE:0.2}
```

DeepSeek 本地环境变量示例：

```powershell
$env:CHAT_MODEL_ENABLED="true"
$env:CHAT_MODEL_BASE_URL="https://api.deepseek.com"
$env:CHAT_MODEL_API_KEY="你的 DeepSeek API Key"
$env:CHAT_MODEL_NAME="deepseek-v4-pro"
$env:CHAT_MODEL_THINKING_ENABLED="true"
$env:CHAT_MODEL_REASONING_EFFORT="high"
```

`deepseek-v4-pro` 会启用 `thinking: {"type": "enabled"}` 和 `reasoning_effort=high`。如果后续切换到不支持这些字段的模型，可以把它们关掉：

```powershell
$env:CHAT_MODEL_THINKING_ENABLED="false"
$env:CHAT_MODEL_REASONING_EFFORT=""
```

Ollama OpenAI-compatible 示例：

```powershell
$env:CHAT_MODEL_ENABLED="true"
$env:CHAT_MODEL_BASE_URL="http://localhost:11434"
$env:CHAT_MODEL_API_KEY="ollama"
$env:CHAT_MODEL_NAME="qwen2.5:7b"
```

具体模型名称要以本机 Ollama 已拉取的模型为准。

## Prompt 设计

系统 Prompt 约束三件事：

- 必须基于引用片段回答。
- 资料不足时必须说明“当前资料不足以确认”。
- 输出格式固定为“结论 / 要点 / 说明”。

用户 Prompt 会携带：

- 用户原始问题。
- 按相关度排序的引用片段。
- 每个片段的文档名、chunk 编号、相关度。

`max-context-chars` 用于限制送入模型的上下文长度，避免一次请求塞入过多 chunk 导致 token 超限。

## 流式输出

系统已支持流式问答接口：

```text
POST /api/rag/ask/stream
```

后端使用 `SseEmitter` 向前端推送事件：

- `citations`：先返回本次召回的引用片段。
- `delta`：大模型每生成一段内容，后端立即转发给前端。
- `complete`：生成结束，返回完整 `RagAskResponse`，同时后端保存问答历史并写入 Redis 缓存。
- `error`：生成失败时返回错误信息。

前端没有使用浏览器原生 `EventSource`，而是使用 `fetch + ReadableStream`。

原因是本系统的问答接口需要：

- 使用 `POST` 提交 JSON body。
- 携带 JWT `Authorization` 请求头。
- 与现有 API 风格保持一致。

原生 `EventSource` 更适合无鉴权或 query 参数型的 `GET` SSE，不适合当前场景。

如果模型未启用或调用失败，后端仍会把本地模板答案按小段输出，保证用户体验一致。

## 降级策略

`ChatModelService.generateAnswer` 返回 `Optional<String>`。

- 有模型答案：使用模型答案。
- 未启用模型：返回空，走本地模板回答。
- 模型调用异常：记录 warn 日志，走本地模板回答。

这样可以保证开发环境没有 Key 也能演示，网络波动也不会让问答功能直接失败。

## 接入状态诊断

后端提供脱敏诊断接口：

```text
GET /api/rag/model/status
```

返回字段：

- `enabled`：是否开启大模型。
- `apiKeyConfigured`：是否已配置 API Key，不返回 Key 明文。
- `available`：是否满足“已开启 + 已配置 Key”。
- `baseUrl`：当前模型服务地址。
- `model`：当前模型名。
- `thinkingEnabled`：是否发送 DeepSeek thinking 参数。
- `reasoningEffort`：推理强度配置。

如果 `enabled=false` 或 `apiKeyConfigured=false`，问答一定会降级成本地模板回答。

## 缓存隔离

问答缓存的 Redis key 会加入回答模式命名空间：

```text
__answer_mode__:local-template
__answer_mode__:openai-compatible:{baseUrl}:{model}
```

原因是同一个问题在不同模式下可能产生不同答案。

如果不隔离缓存，就会出现这种问题：

1. 未配置大模型时，用户提问并缓存了本地模板答案。
2. 后续开启大模型。
3. 用户再次问同一个问题，系统直接命中旧缓存，导致看起来“大模型没有生效”。

因此当前实现把本地降级答案和不同模型生成的答案分开缓存。

## 后续升级方向

- 增加模型调用耗时、成功率、降级次数统计。
- 支持在前端显示回答来源：大模型生成 / 本地降级。
- 支持多模型配置：默认模型、长文本模型、本地模型。
- 支持流式输出。
- 将 Prompt 模板外置到配置或数据库。

## 回答来源与调用观测

系统已经在 RAG 问答返回值和问答历史中加入模型调用观测字段：

- `answerSource`：回答来源。`MODEL` 表示真实大模型生成，`LOCAL_FALLBACK` 表示本地模板回答。
- `modelName`：本次真实调用的模型名，例如 `deepseek-v4-pro`。
- `latencyMs`：本次问答链路耗时，单位毫秒。
- `cacheHit`：是否命中 Redis 问答缓存。
- `fallback`：是否发生模型降级。模型已启用但调用失败时会标记为 `true`。

这些字段会同时出现在：

```text
POST /api/rag/ask
POST /api/rag/ask/stream
GET /api/rag/history
```

前端回答卡片会展示“DeepSeek 生成 / 缓存命中 / 本地回答 / 模型降级”、模型名和耗时。这样排查问题时可以直接判断：

1. 当前回答是否真的来自 DeepSeek。
2. 是否因为 Redis 缓存看起来“没有重新调用模型”。
3. 模型调用失败后是否自动降级到了本地模板。
4. 单次问答耗时是否异常。

面试表达可以这样说：

```text
我没有只做一个黑盒式的大模型调用，而是在 RAG 返回结果里加入了可观测元数据，包括回答来源、模型名、耗时、缓存命中和降级状态。这样可以从前端和历史记录直接判断一次回答到底来自真实模型、Redis 缓存还是本地降级，方便排查线上问题，也能为后续统计模型成功率和耗时分布打基础。
```
